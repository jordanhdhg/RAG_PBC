# 通用硬件 RAG 前端开发方向

更新时间：2026-10-07（Asia/Shanghai）  
文档性质：前端与产品化方向讨论，不构成当前实施授权。

## 1. 当前判断

目前通用硬件 RAG 主要通过 CLI 使用。CLI 对开发者和测试人员友好，但对普通工程师存在明显门槛：

- 需要打开 PowerShell。
- 需要进入项目目录。
- 需要加载 D 盘独立环境。
- 需要理解 search、ask、route 等命令。
- 需要记住配置文件和筛选参数。
- 需要理解命令行输出中的引用信息。

如果希望让更多人使用，增加图形化界面是合理方向。最适合当前项目的形式不是单独写一个静态 HTML，而是：

    HTML + CSS + JavaScript 前端
             ↓
    Python Web API 后端
             ↓
    现有 RAG 检索与回答模块

也就是说，不需要重做 RAG 核心，而是为现有 RAG 增加面向普通用户的产品外壳。

## 2. 为什么不能只做一个 HTML 文件

浏览器中的静态 HTML 页面不能直接完成以下工作：

- 加载 BGE-M3 模型。
- 访问本地 Qdrant 索引文件。
- 读取 BM25 索引。
- 调用 Python 检索模块。
- 安全保存 DeepSeek API Key。
- 执行资料解析和索引维护。

因此必须增加后端服务。HTML 负责界面和用户交互，Python 后端负责真正的 RAG 工作。

## 3. 推荐技术方案

第一版建议使用：

- 后端：FastAPI。
- 前端：原生 HTML、CSS、JavaScript。
- RAG 核心：继续复用现有 Python 模块。
- 向量检索：现有本地 BGE-M3 和 Qdrant。
- 关键词检索：现有 BM25。
- 在线回答：由后端调用 DeepSeek。
- 部署方式：先本机运行，验证后再部署到公司内网。

暂时不建议一开始使用 React、Vue 或复杂桌面框架。当前主要功能是输入问题、选择范围、显示证据和显示回答，原生 HTML 已经足够。

Streamlit 或 Gradio 可以用于很快制作演示原型，但长期正式架构建议使用 FastAPI 加独立的 HTML/JavaScript 界面。

## 4. 推荐系统架构

    用户浏览器
        ↓
    index.html + JavaScript
        ↓ HTTP 请求
    FastAPI Web 服务
        ├─ 路由解析
        ├─ 本地检索
        ├─ 引用验证
        ├─ DeepSeek 回答
        └─ 错误处理
        ↓
    现有 RAG 核心
        ├─ query_scope.py
        ├─ retriever.py
        ├─ answerer.py
        ├─ citations.py
        ├─ BGE-M3
        ├─ Qdrant
        └─ BM25

当前项目已经有 query_scope.py、retriever.py、answerer.py、citations.py 等核心模块，因此网页开发的重点是增加 Web API 和界面，而不是重写检索算法。

## 5. 第一版网页应包含的功能

页面可以先保持简单，包含：

- 问题输入框。
- 领域下拉框。
- 主题下拉框。
- 器件型号下拉框。
- DDR 类型下拉框。
- 接口下拉框。
- 仅本地检索按钮。
- 生成答案按钮。
- 当前路由范围显示。
- 检索结果列表。
- [C1]、[C2] 等证据编号。
- 文档名称、版本、章节和页码。
- 原文摘录。
- 答案来源。
- 未审核资料提示。
- API 或本地检索错误提示。
- 模型加载和查询进度提示。

建议明确区分两个按钮：

    仅本地检索
    = route + search
    = 不调用 DeepSeek
    = 只显示原文证据

    生成答案
    = route + search + ask
    = 调用 DeepSeek
    = 显示整理后的答案和引用

这样用户不会误以为每一次搜索都会产生 API 费用。

## 6. API 设计方向

### 6.1 服务状态

    GET /api/health

用于检查：

- Web 服务是否运行。
- BGE-M3 是否加载。
- Qdrant 是否可用。
- BM25 是否可用。
- 当前是否允许在线生成。

示例返回：

    {
      "status": "ok",
      "model_loaded": true,
      "qdrant": "ready",
      "bm25": "ready",
      "generation_enabled": false
    }

### 6.2 获取筛选选项

    GET /api/options

返回：

- 领域。
- 主题。
- DDR 类型。
- 接口。
- 已登记型号。
- 已登记资料。

前端据此动态生成下拉菜单，避免把筛选选项重复写死在 HTML 中。

### 6.3 路由判断

    POST /api/route

请求内容可以包括：

    {
      "query": "GW2A 的 VCCX 与 VCCIO 上电顺序是什么？",
      "domains": ["power_management"],
      "topics": [],
      "part": "GW2A",
      "memory_type": null,
      "interface": null,
      "doc_id": null
    }

成功时返回：

    {
      "status": "resolved",
      "domains": ["power_management"],
      "topics": ["power_supply", "power_sequencing"],
      "parts": ["GW2A"],
      "reason": "explicit domain"
    }

无法判断领域时返回 clarification_required，并提示用户选择领域。网页不应在范围不确定时继续检索或调用回答模型。

### 6.4 本地检索

    POST /api/search

请求内容与 route 相同，并增加：

    {
      "mode": "hybrid",
      "limit": 6
    }

返回内容应包含：

- route。
- citation_id。
- score。
- 文档 ID。
- 文档标题。
- 文档版本。
- 章节。
- PDF 页码或幻灯片号。
- 领域和主题。
- 来源身份。
- 原文摘录。

前端将每条结果显示为一个证据卡片。

### 6.5 在线回答

    POST /api/ask

后端执行：

    解析范围
      ↓
    本地检索
      ↓
    选择最多 6 条证据
      ↓
    调用 DeepSeek
      ↓
    验证 [C#] 引用
      ↓
    返回答案

返回内容应包含：

- answer。
- citations。
- retrieved。
- route。
- 是否发生拒答。
- 错误或证据不足提示。

DeepSeek API Key 只能保存在后端，绝不能放入 HTML 或 JavaScript。

## 7. 后端调用方式

不建议每次点击按钮都通过 Web 服务启动一个新的 CLI 子进程：

    网页
      ↓
    PowerShell
      ↓
    Python
      ↓
    加载模型
      ↓
    检索

这样会导致启动慢、模型重复加载和错误处理复杂。

更合理的方式是：

    网页
      ↓
    FastAPI
      ↓
    直接调用现有 Python 模块

后端启动时可以预加载：

- BGE-M3。
- Qdrant。
- BM25。
- V2 配置。
- 资料目录。

这样模型只加载一次，后续查询更快，也更容易实现并发和统一错误处理。

## 8. 开发阶段规划

### 阶段一：后端 API 封装

先不制作复杂界面，只让 API 工作。

计划接口：

- /api/health
- /api/options
- /api/route
- /api/search
- /api/ask

验收重点：

- API 是否能调用现有检索逻辑。
- JSON 字段是否完整。
- 网页 API 与 CLI 的引用是否一致。
- 歧义问题是否停止。
- 在线回答是否最多发送 6 条证据。
- 引用校验是否继续有效。
- 离线 search 是否绝不调用 DeepSeek。

### 阶段二：制作原生 HTML 页面

使用 HTML、CSS 和 JavaScript 实现：

- 输入框。
- 筛选下拉框。
- 本地检索按钮。
- 生成答案按钮。
- 证据卡片。
- 答案区域。
- 引用来源区域。
- 错误提示。
- 加载进度提示。

第一版不需要复杂视觉设计，重点是检索范围和引用是否清楚。

### 阶段三：本机一键启动

制作一个启动器，使用户不再输入 CLI：

    双击通用硬件 RAG.exe
        ↓
    启动本地 FastAPI 服务
        ↓
    等待服务就绪
        ↓
    自动打开浏览器或内置窗口

这一步仍然是本地运行，但用户体验已经接近普通软件。

### 阶段四：制作 Windows 安装程序

安装包可以包含：

- RAG 桌面启动器。
- 精简 Python 运行环境。
- Web 后端。
- HTML、CSS、JavaScript 页面。
- V2 配置。
- Qdrant 和 BM25 索引。
- 必要的资料元数据。
- 模型或模型下载器。

安装程序负责释放文件和创建快捷方式，用户不需要接触 Python 或 PowerShell。

### 阶段五：内部服务器部署

如果需要多人使用，可以将模型、资料和索引集中到服务器：

    用户浏览器
        ↓
    公司内部 Web 服务
        ↓
    统一 RAG 模型、资料和索引

此时用户电脑不需要重复安装 BGE-M3 和完整 Python 环境。

### 阶段六：资料管理员功能

资料上传、解析、切块、Embedding、索引重建等功能应单独做成管理员入口，不应直接开放给普通用户。

普通用户只应拥有：

- 检索。
- 查看证据。
- 生成回答。
- 查看来源。

## 9. 本地网页与内网网页的选择

### 本地网页

用户电脑运行 RAG 服务，浏览器访问 localhost。

适合：

- 个人使用。
- 少量用户。
- 保密资料。
- 完全离线场景。

缺点是每台电脑都要安装模型和索引。

### 内网网页

服务器运行 RAG 服务，所有用户通过浏览器访问。

适合：

- 公司内部多人使用。
- 资料统一维护。
- 经常更新资料。
- 用户电脑配置不一致。

缺点是需要服务器、账号、权限和并发控制。

## 10. 安全设计

网页化后必须增加以下安全边界：

- DeepSeek Key 只能保存在后端。
- 浏览器不能直接访问 DeepSeek。
- 浏览器不能直接读取 Qdrant 文件。
- 普通用户不能调用 parse、chunk、embed、index 或 ingest。
- 不允许用户通过请求参数读取任意本地文件。
- 返回原文时只返回已验证的来源片段。
- 对 ask 设置调用频率限制。
- 对在线回答记录请求数量和费用。
- 对不同用户设置资料访问权限。
- 资料涉密时优先采用本地或内网部署。
- 对服务器上的索引和原始资料定期备份。

## 11. 安装包和体积规划

当前项目中较大的部分主要是 Python 环境和模型，而不是 Qdrant/BM25 索引。

当前完整开发环境约 4.94 GiB，本地模型缓存约 4.74 GiB；但普通用户不需要安装全部资料解析和开发依赖。

建议拆分：

    普通用户版
      ├─ 精简运行环境
      ├─ RAG 检索模块
      ├─ BGE-M3
      ├─ Qdrant/BM25 索引
      └─ 界面

    管理员版
      ├─ Docling
      ├─ 资料解析工具
      ├─ Chunk 工具
      ├─ Embedding 工具
      ├─ 索引重建工具
      └─ 原始资料管理

模型可以有三种分发方式：

1. 完整离线安装包：安装包大，但安装后无需联网。
2. 小型安装器：首次启动时单独下载模型。
3. 内网集中部署：模型只放在服务器，用户电脑不重复安装。

## 12. 不建议第一版就做的内容

第一版不建议立即加入：

- 公网访问。
- 复杂账号系统。
- 普通用户上传资料。
- 普通用户重建索引。
- 多模型切换。
- 移动端。
- 复杂 React/Vue 前端。
- Agent。
- EDA API。
- 自动修改 PCB。
- 在线自动抓取资料。

第一版先稳定完成：

    输入问题
      → 判断范围
      → 返回本地证据
      → 可选生成带引用答案

## 13. 推荐路线

结合当前项目，推荐：

### 第一阶段

    FastAPI + 原生 HTML/CSS/JavaScript
    本机运行
    支持 route、search、ask
    保留 CLI 作为管理员和调试入口

### 第二阶段

    打包成 Windows 安装程序
    用户双击启动
    自动打开本地网页窗口
    用户不接触 CLI

### 第三阶段

    部署到公司内网服务器
    所有用户使用浏览器访问
    统一管理模型、资料和 API Key

## 14. 最终结论

前端开发的目标不是把 RAG 改写成 HTML，而是：

    给现有 RAG 增加一个 HTML 前端和一个 Web API 后端

当前项目的 RAG 核心、分类、检索、引用和回答逻辑可以继续保留。网页端主要解决用户入口、参数选择、结果展示和部署问题。

最适合的起点是本机运行的 FastAPI + 原生 HTML 页面；验证体验后，再决定是制作本地桌面安装版，还是部署成公司内部统一网页服务。
