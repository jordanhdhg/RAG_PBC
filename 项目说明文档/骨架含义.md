# DDR RAG 项目骨架含义

本文依据 `plan.md` 中的“目录骨架”编写，并结合当前项目目录说明每个目录、文件和程序模块的职责。

> 状态说明：
>
> - **已有**：当前项目中已经存在；
> - **规划中**：计划定义了职责，但对应文件或功能尚未落地；
> - **运行时生成**：执行解析、切分、向量化或测试后自动产生，不应手工编辑。

## 1. 项目根目录

项目根目录是 `D:\pcb\AI_PCB\`。它保存项目配置、程序源码、文档资料、测试与运行结果。

| 文件或目录 | 状态 | 含义与用途 |
|---|---|---|
| `plan.md` | 已有 | 项目执行计划和目标架构。定义 RAG 流程、技术选型、目录骨架、阶段任务、CLI 目标和验收标准。它是“要建设成什么样”的说明，不等同于所有功能已经完成。 |
| `README.md` | 已有 | 项目使用说明。面向使用者介绍如何启用虚拟环境、登记 PDF、运行资料校验、解析文档等。后续应补充完整安装、检索和评估说明。 |

| `.env.example` | 骨架文件 | 环境变量模板。应只保留变量名和示例，不放真实 API Key；用户复制为 `.env` 后再填写本机密钥。 |
| `.gitignore` | 骨架文件 | 版本控制忽略规则。用于避免把 `.venv`、真实 `.env`、模型缓存、索引、日志、临时文件或大体积结果误加入版本控制。 |
| `config.yaml` | 已有 | 项目的集中配置文件。定义路径、Docling 解析参数、Chunk Token 上限、Embedding 模型、检索参数、生成模型和日志策略，避免把这些参数写死在程序中。 |
| `AGENT.md` | 已有，项目管理文件 | 项目执行规则，例如遇到问题时记录到 `出现问题.md`。它不是 RAG 程序代码。 |
| `交接.md` | 已有，项目管理文件 | 记录当前阶段、已完成内容、验证结果和下一步，便于后续继续项目时不重复工作。 |
| `执行过程.md` | 已有，项目管理文件 | 按时间记录实际执行的操作与验证结果。 |
| `出现问题.md` | 已有，项目管理文件 | 记录执行期间遇到的问题、原因、解决方案、验证方式和后续注意事项。 |
| `资料整理.md` | 已有，项目资料文件 | 收集外部技术资料的官方地址及简要说明，例如 PyTorch、Qdrant、Docling 和 RAG 论文。 |
| `知识补充.md` | 已有，项目资料文件 | 用于补充与 DDR RAG 相关的知识、结论或待确认事项，不是程序运行所必需的配置。 |
| `骨架含义.md` | 已有，说明文件 | 本文件，解释项目骨架及各组成部分的作用。 |

## 2. `data/`：资料、处理中间结果与检索数据

`data/` 是项目的数据层。原则上，原始资料、解析结果、切分结果、模型缓存和索引结果都放在此处，而不与 Python 源代码混在一起。

```text
data/
├─ raw/
├─ catalog/
├─ parsed/
├─ chunks/
├─ index/
├─ cache/          # 当前运行时目录
└─ models/         # 当前运行时目录
```

### 2.1 `data/raw/`：原始资料库

`raw/` 存放未经程序修改的源文件，主要是 PDF。RAG 的所有内容都应该能追溯回这里的原始资料。

| 子目录 | 含义 | 应放入的资料 |
|---|---|---|
| `data/raw/vendor/` | 芯片或存储器厂商资料 | NXP、TI、瑞芯微、DDR 颗粒厂商的硬件设计指南、布局指南、数据手册等。 |
| `data/raw/standards/` | 行业标准资料 | JEDEC 标准、DDR 接口规范或公开标准文件。 |
| `data/raw/company/` | 公司内部规范 | 已授权使用的内部设计规范、检查表或流程文件。 |
| `data/raw/fab/` | PCB 板厂能力资料 | 叠层、线宽线距、阻抗控制、公差和制造约束资料。 |
| `data/raw/experience/` | 已审核工程经验 | 已验证的 DDR 设计复盘、问题案例、经验总结。未审核或来源不明的结论不应直接放入。 |

原始 PDF 不应被程序覆盖、编辑或修改。若资料更新，应新增新版本文件，并在目录登记信息中体现版本关系。

### 2.2 `data/catalog/`：资料登记信息

| 文件 | 状态 | 含义与用途 |
|---|---|---|
| `documents.yaml` | 已有 | 文档目录（Catalog）。每份原始资料都应有一条记录，包含 `doc_id`、标题、版本、来源路径、DDR 类型、适用芯片、文档状态、权威性、保密等级、SHA-256 等元数据。解析、切分、检索和引用通过 `doc_id` 关联同一份资料。 |

### 2.3 `data/parsed/`：Docling 解析结果

该目录保存 PDF 经 Docling 解析后的结构化中间结果。它不是原始 PDF，也不是最终向量索引。

| 子目录 | 含义与用途 |
|---|---|
| `data/parsed/JSON/` | 已有。保存 Docling JSON，包含文档层级、段落、表格、页码、坐标等结构化信息。切分程序主要依赖此文件保留章节和页面来源。 |
| `data/parsed/Markdown/` | 已有。保存更便于人工阅读、检查和排错的 Markdown 文本。可用于快速检查解析出来的标题、正文和表格是否合理。 |

### 2.4 `data/chunks/`：切分后的 RAG 最小证据单元

| 文件 | 状态 | 含义与用途 |
|---|---|---|
| `chunks.jsonl` | 已有，运行时生成 | HybridChunker 输出的 Chunk 文件。JSONL 表示“一行一个 JSON 对象”，便于流式读取。每个 Chunk 保留 `chunk_id`、文档 ID、标题、版本、来源路径、章节、页码、DDR 类型、文档状态、正文和 Token 数等元数据。Embedding、检索和引用都以此文件为输入。 |

### 2.5 `data/index/`：向量与检索索引

该目录保存可重新生成的检索数据，不保存原始资料。

| 内容 | 状态 | 含义与用途 |
|---|---|---|
| `data/index/bge-m3/` | 已有，运行时生成 | 本地 BGE-M3 生成的向量产物目录。通常包括向量矩阵、Chunk ID 映射及清单文件，保证“第 N 个向量”能准确对应到某个 Chunk。 |
| Qdrant Local 数据 | 规划中 | 后续 Qdrant Local Mode 的持久化索引目录。将保存 dense/sparse 检索所需的数据库文件，程序重启后仍能使用。 |

### 2.6 `data/cache/`：下载缓存

| 子目录 | 含义与用途 |
|---|---|
| `data/cache/pip/` | pip 下载的安装包缓存。将缓存放在 D 盘，避免占用 C 盘。删除后不会删除已安装的 Python 包，但未来安装时需要重新下载。 |
| `data/cache/huggingface/` | Hugging Face 模型和元数据下载缓存。BGE-M3 等模型下载时使用，放在 D 盘以避免占用 C 盘。 |

### 2.7 `data/models/`：本地模型文件

| 子目录 | 含义与用途 |
|---|---|
| `data/models/bge-m3/` | 本地 BGE-M3 模型的指定缓存位置。模型用于把文本 Chunk 编码成向量；它不是检索结果，也不是原始 DDR 资料。 |

## 3. `src/`：Python 源代码

`src/` 使用 Python 的 src-layout。这样安装项目时，只有经过安装或测试配置认可的代码才能被导入，有助于避免从错误位置导入模块。

```text
src/
├─ ddr_rag/
└─ ddr_rag.egg-info/
```

### 3.1 `src/ddr_rag/`：核心程序包

这是 DDR RAG 的主程序目录。命令 `python -m ddr_rag ...` 和 `ddr-rag ...` 都从这里启动。

| 文件 | 状态 | 含义与用途 |
|---|---|---|
| `__init__.py` | 已有 | 将 `ddr_rag` 声明为 Python 包；可存放包版本或最小初始化逻辑。 |
| `__main__.py` | 已有 | 支持使用 `python -m ddr_rag` 启动 CLI；通常负责调用 `cli.py` 中的应用入口。 |
| `config.py` | 已有 | 读取 `config.yaml` 和环境变量，使用 Pydantic 校验配置，解析项目相对路径为实际路径，并校验 Token 上限、批大小、模型配置等。 |
| `schemas.py` | 已有 | 定义项目中的数据结构和字段校验规则，如 `DocumentRecord`、`ChunkRecord`、`Citation`、`SearchResult`、`AnswerResult`、资料校验报告等。它保证不同模块使用相同的数据格式。 |
| `catalog.py` | 已有 | 读取 `documents.yaml`，计算文件 SHA-256，并校验文档 ID 唯一性、文件存在性、文件是否在 `data/raw` 下、状态和版本字段等。 |
| `parser.py` | 已有 | 调用 Docling 解析已登记 PDF，输出 Markdown 和 JSON，保留表格与页码来源，并在 `logs/ingestion/` 写入解析过程日志。 |
| `chunker.py` | 已有 | 从 Docling JSON 读取结构化文档，调用 HybridChunker 按层级和 Token 限制切分；生成带完整来源元数据的 `ChunkRecord`，并写入 `chunks.jsonl`。 |
| `embedder.py` | 已有 | 读取 `chunks.jsonl`，加载本地 BGE-M3，使用 GPU 或 CPU 生成向量；写入向量、Chunk 映射与清单，并校验向量与 Chunk 的对应关系。它只负责向量化，不负责 Qdrant 入库或问答。 |
| `vector_store.py` | 规划中 | Qdrant 的封装层。负责创建集合、定义 dense/sparse 向量字段、写入或删除 Point、检查索引与 Embedding 模型是否匹配。 |
| `ingest.py` | 规划中 | 入库编排层。将“解析、切分、Embedding、写入 Qdrant”按文档或全量执行，处理重复执行、文档更新和显式 `--replace`。 |
| `retriever.py` | 规划中 | 检索层。接收问题及 DDR 类型、芯片型号、文档状态等过滤条件，执行 dense 检索和 BM25 sparse 检索，并用 RRF 融合结果。 |
| `answerer.py` | 规划中 | 可选问答层。把检索到的真实证据组织为提示词，调用启用的回答模型生成答案；必须在未启用 API 时给出明确提示。 |
| `citations.py` | 规划中 | 引用层。根据真实 `chunk_id` 建立文档、版本、章节和页码引用，防止回答模块凭空编造来源。 |
| `cli.py` | 已有 | Typer 命令行入口。当前承载 `catalog validate`、`parse`、`chunk`、`embed` 等命令；后续将增加 `ingest`、`search`、`ask` 和 `eval`。 |

### 3.2 `src/ddr_rag.egg-info/`：安装元数据

该目录由 Python 打包工具自动生成，记录已安装项目的名称、版本、依赖、入口命令和源码清单。

| 文件 | 含义与用途 |
|---|---|
| `PKG-INFO` | 项目名称、版本、依赖等打包元数据。 |
| `requires.txt` | 安装时需要的依赖列表。 |
| `entry_points.txt` | 命令行入口定义，例如 `ddr-rag` 指向 `ddr_rag.cli:app`。 |
| `top_level.txt` | 顶层 Python 包名。 |
| `SOURCES.txt` | 打包时包含的源码文件清单。 |
| `dependency_links.txt` | 旧式依赖链接元数据；通常为空或不需要手工处理。 |

此目录为自动生成内容，通常不手工编辑。

### 3.3 `__pycache__/`：Python 字节码缓存

`src/ddr_rag/__pycache__/` 和 `tests/__pycache__/` 中的 `.pyc` 文件是 Python 为加快下次导入而生成的字节码缓存。它们不是源代码，不需要阅读或手工编辑，通常应由 `.gitignore` 忽略。

## 4. `prompts/`：问答提示词

| 文件 | 状态 | 含义与用途 |
|---|---|---|
| `answer_system.txt` | 规划中 | 给可选回答模型使用的系统提示词。应明确要求：只基于提供的 Chunk 回答、不能编造引用、证据不足时明确拒答、冲突资料要并列展示。将提示词独立成文件，方便审阅、版本管理和调整。 |

## 5. `evals/`：检索与问答评估

`evals/` 用于验证 RAG 是否真正能找到正确资料，而不只是程序能运行。

| 文件或目录 | 状态 | 含义与用途 |
|---|---|---|
| `questions.yaml` | 规划中 | 测试问题集。计划包含可回答问题和不可回答问题，覆盖中英文查询、DDR 类型、数值、型号、版本冲突等情况。 |
| `expected_sources.yaml` | 规划中 | 每个测试问题期望命中的文档、章节、页码或 Chunk。用于自动判断 Top-K 是否包含正确证据。 |
| `results/` | 已有目录，运行时生成 | 保存每次评估运行结果，例如命中率、拒答率、失败案例与参数。方便比较模型、切分策略和检索参数的变化。 |

## 6. `logs/`：运行日志

日志用于排错、审计和复现，不应记录 API Key 或其他敏感信息。

| 子目录 | 状态 | 含义与用途 |
|---|---|---|
| `logs/ingestion/` | 已有 | 记录资料解析、切分、向量生成和后续入库的处理结果与错误。例如当前已有各 PDF 的 `.parse.json` 处理日志。 |
| `logs/queries/` | 已有目录 | 后续保存检索请求、命中 Chunk、过滤条件和问答结果。是否保存由 `config.yaml` 的 logging 配置控制。 |

测试用于确认改动没有破坏已有能力。测试文件本身是程序，不是用户资料。

| 文件 | 状态 | 含义与用途 |
|---|---|---|
| `test_catalog.py` | 已有 | 测试文档目录读取与校验，例如空目录警告、PDF 是否存在、重复文档 ID 等。 |
| `test_config.py` | 已有，骨架扩展项 | 测试配置读取、路径解析和非法切分参数拒绝等。 |
| `test_chunking.py` | 已有 | 测试 Chunk 的必需元数据、页码来源、Token 超限拆分、页码范围校验和覆盖写入保护。 |

## 9. 完整 RAG 数据流与目录对应关系

```text
原始 DDR PDF
data/raw/vendor/ 等目录
        ↓ 文档登记
data/catalog/documents.yaml
        ↓ Docling 解析
data/parsed/JSON/ + data/parsed/Markdown/
        ↓ HybridChunker 切分
data/chunks/chunks.jsonl
        ↓ BGE-M3 向量化
data/index/bge-m3/
        ↓ 后续 Qdrant 入库
data/index/ 中的 Qdrant Local 数据
        ↓ Dense + Sparse + RRF 检索
检索证据（Chunk、文档、版本、章节、页码）
        ↓ 可选回答模块
带真实来源引用的 DDR 问答结果
```

## 10. 使用时最重要的边界

1. `data/raw/` 中的原始 PDF 是证据源，不能被程序覆盖。
2. `documents.yaml` 是原始 PDF 与后续所有产物之间的登记桥梁；未登记资料不应直接进入处理流程。
3. `parsed/`、`chunks/`、`index/`、`logs/` 都是可根据原始资料重新生成的产物，但重新生成时应遵守版本与 `--replace` 保护规则。
4. `src/ddr_rag/` 是程序代码；`data/` 是资料和运行数据；`tests/` 是验证程序；`evals/` 是验证检索质量。四者职责不同，不应混放。
5. 本地 BGE-M3 只负责生成向量；Qdrant、混合检索、引用和自动问答仍属于后续独立阶段。
