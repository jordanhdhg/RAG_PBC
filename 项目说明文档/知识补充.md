# 知识补充

## 2026-09-21：Docling、Chunk 与侧边对话

### 1. Docling 是什么，是否需要配置？

Docling 是用于解析文档的程序库（Python 工具），不是人工操作步骤。需要在项目环境中安装并做一次配置；之后由程序自动读取 PDF，输出适合后续处理的结构化结果，例如 Markdown 和 JSON。

它的作用不是简单地把 PDF 转成纯文字，而是尽量保留标题层级、段落、表格、页码等结构。对于 DDR Datasheet 和 Hardware Design Guide，这些结构决定了规则的适用条件能否被正确保留。

### 2. Chunk 应该由谁来切？

Chunk 主要由程序自动切分，不应手工逐段切分。理想流程是：

```text
原始 PDF
  → Docling 解析为结构化文档
  → Chunk 程序按章节、小节、段落、表格和 Token 上限切分
  → 生成可检索的 chunks.jsonl
```

切分时应优先保留完整的工程语义单元：标题、适用条件、规则正文、表格和例外说明应尽量处于同一个 Chunk 中。不能只按固定字符数硬切，否则可能出现数值规则与其速率、器件或拓扑条件分离的问题。

### 3. 人与程序各自负责什么？

| 环节 | 主要负责者 | 说明 |
| --- | --- | --- |
| 原始资料归档、确认版本与适用范围 | 工程师 | 决定资料是否可信、适用于哪类 DDR 项目。 |
| 文档登记 | 工程师为主 | 在 `documents.yaml` 中记录型号、版本、DDR 类型、状态等。 |
| PDF 解析 | 程序 | 由 Docling 自动执行。 |
| Chunk 切分 | 程序 | 由切分程序自动执行。 |
| 关键资料解析与切分效果抽查 | 工程师 | 确认表格、页码、条件和例外没有被破坏。 |
| 切分策略、解析与入库程序 | Codex 协助 | 根据资料特点设计、实现和调整。 |
| 最终工程结论审核 | 工程师 | RAG 回答必须回到原始资料核验。 |

### 4. 侧边对话与主对话的边界

侧边对话可以读取分支开始前继承的主对话历史，用作背景参考；但它是独立对话，不会自动继续主对话中的任务、执行命令或修改文件。主对话在分支之后的新内容不会自动同步到侧边对话。

## 2026-09-21：回答模型、Embedding 模型与索引重建

### 1. 更换回答模型与更换 Embedding 模型的区别

RAG 中通常有两类模型：

```text
Embedding 模型：负责把文档和问题转成向量，用于检索
回答模型（LLM）：负责阅读检索到的证据并生成答案
```

因此，更换回答模型通常不需要重建知识库或向量索引。只要检索结果不变，换回答模型主要影响回答质量、风格、速度和成本。

更换 Embedding 模型则通常必须重新生成全部文档 Chunk 的向量并重建向量索引，因为不同 Embedding 模型的向量维度、数值分布和向量空间可能不同。文档向量和问题向量必须由同一个 Embedding 模型生成。

更准确地说，更换 Embedding 模型时不一定要重新解析原始 PDF。若已有的解析结果和 `chunks.jsonl` 仍然有效，可以复用它们，只重新执行：

```text
chunks.jsonl
  → 新 Embedding 模型
  → 新的向量索引
```

### 2. 哪些变化需要重新建立向量索引

- 更换 Embedding 模型或 Embedding 模型版本：需要重新生成向量。
- 修改 Chunk 切分策略：需要重新生成 Chunk 和向量。
- 原始文档版本更新：更新部分需要重新解析、切分和索引。
- 修改用于检索的元数据，例如 DDR 类型、芯片型号、文档状态：需要更新索引元数据。
- 仅更换回答模型、回答提示词或回答格式：通常不需要重建向量索引。

### 3. Embedding 模型与 GPT 的区别

Embedding 模型专门把文本转换为向量，用于判断问题和文档片段的语义相关性。GPT 主要负责理解问题、阅读上下文、推理和生成自然语言答案。

在 DDR RAG 中，典型流程是：

```text
DDR 文档
  → Embedding 模型
  → Qdrant 向量索引
  → 检索相关 Chunk
  → GPT 或其他 LLM
  → 带引用的工程回答
```

GPT 内部虽然也有用于处理 Token 的 Embedding 层，但这不等于 GPT 就是面向 RAG 检索的 Embedding 模型。RAG 通常使用独立的 Embedding 模型和独立的回答模型。

### 4. Embedding 模型的类型与选择原则

常见选择分为：

- 在线 API Embedding：部署简单，但需要考虑资料外发、费用和服务依赖。
- 本地开源 Embedding：资料可留在本地，但需要自行部署模型和评估资源占用。

由于 DDR 资料经常是英文，而工程师可能用中文提问，第一版应优先选择支持中英文跨语言检索的 Embedding 模型，并用实际中文问题检索英文 DDR 文档进行验证。

## 2026-09-23：DDR RAG 建议的学习顺序

不要一开始钻研 Agent、MCP、LangChain 或复杂工作流。先按项目自身流程学习：

### 1. 理解 RAG 数据流

阅读 [LlamaIndex RAG CLI 概念说明](https://llamaindex.openml.io/python/framework/getting_started/starter_tools/rag_cli/)，只关注“资料 → 检索结果 → 上下文 → LLM”这条链。

### 2. 掌握当前项目最关键的切分

阅读 [Docling HybridChunker 示例](https://docling-project.github.io/docling/_generated/examples/hybrid_chunking/)。重点理解 Token、标题层级、表格表头、Chunk 元数据。

### 3. 理解向量和 Qdrant

学习 [Qdrant Local Quickstart](https://qdrant.tech/documentation/quickstart/)，重点是 collection、vector、payload、filter、query 五个词。

对本项目而言，`payload` 就是 `doc_id`、页码、章节、DDR 类型、状态等工程元数据。

### 4. 理解在线 API 调用

阅读 [OpenAI API 快速开始](https://developers.openai.com/api/docs/quickstart)，重点理解 `API Key`、`model`、`input`、`response.output_text`。

### 5. 理解“检索后再回答”

阅读 [OpenAI Retrieval 指南](https://developers.openai.com/api/docs/guides/retrieval)的“Semantic search”和“Synthesizing responses”。它展示了云端托管检索路线；本项目采用本地 Qdrant，但“先搜证据、再把证据和问题交给模型”的逻辑相同。

搜索资料时可直接使用这些关键词：

```text
RAG pipeline chunking embedding vector database retrieval generation
Docling HybridChunker contextualize metadata
Qdrant local mode payload filter hybrid search
OpenAI Responses API Python grounding citations
RAG evaluation retrieval recall citation correctness
```

最后，区分以下三件事情即可避免大多数概念混乱：

```text
模型供应商配置（OpenAI / 其他 API）
      ≠
RAG 知识库与检索（Docling / Chunk / Qdrant）
      ≠
Agent 工具编排（以后才考虑）
```
